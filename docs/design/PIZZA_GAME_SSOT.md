## 1. プロジェクトの目的

[PIZZA DB](https://pizzadb.jp/) が持つ「ピザという食文化を分類し、楽しく検索する」世界観・UX を参考に、
スマートフォン向けの **「実際にピザを作るゲーム」** を開発する。

PIZZA DB のテキスト・画像・データそのものは一切使用しない。分類の考え方・UX の空気感・ピザ文化への
リスペクトのみを参考にする。ゲーム内のレシピデータは完全に独自データとして設計・管理する。

## 2. 最重要目標: First Fun Pizza

> **経営機能を広げることではなく、「1枚のピザを作るだけで楽しい」体験を完成させる。**

- 店舗経営、収益管理、拡張要素は今回のゴールではない。
- プレイヤーが **自分の手でピザを作った** という手触り・満足感を最優先する。
- 「材料を選んでクイズに正解する」ゲームには絶対にしない。
  - ソースを塗る、チーズやトッピングをピザの上に配置する、という **actionable な操作** を通じて
    「自分で作った」感覚を作ることが最優先の設計目標。
- 1枚のマルゲリータが気持ちよく完成する体験の品質が、機能量よりも重要。

## 3. MVP範囲（Phase 0 + Phase 1 で扱う範囲・完了済み）

- レシピ: マルゲリータ 1種類のみ
- キャラクター: テト（主人公・ピザ職人）、ミト（注文・案内・ヒント）、ブルー（試食・評価）
- ゲームループ: 注文 → 生地の準備（ソース・チーズ・トッピング配置）→ 焼成 → 試食・採点 → 図鑑登録 → 再プレイ
- プラットフォーム: スマートフォン縦画面が主、Web でもタッチ/クリック操作で遊べること
- データとUIの分離: レシピ・食材・注文をデータとして定義し、後から追加できる設計

Phase 1 は上記完成条件（本ドキュメント第11章）をすべて満たして完了し、GitHub Pages で
Public Demo として公開済みである。

## 3A. Phase 2A 範囲（確定・本フェーズの実装対象）

**最重要目標（変わらず）**: 機能を増やすことではなく、「1枚作るだけで楽しく、もう1枚作りたくなる」
First Fun Pizza 体験を強化する。経営要素（お金・在庫・ログイン・サーバー・ランキング等）は一切追加しない。

Phase 2A で確定するスコープ:

1. **複数レシピ（3種）**: マルゲリータに加え、マリナーラ・クアトロ フォルマッジを追加する。
   いずれも実在するピザとして自然な材料構成にする（架空の食材の組み合わせにしない）。
   マリナーラはナポリの伝統に倣いチーズを使わない（トマトソース・にんにく・オレガノ）。
   既存の data-driven 構造（`ingredients.ts` / `recipes.ts` / `orders.ts`）はそのまま拡張し、
   UI コンポーネント側の変更を最小限にする方針を維持する。
2. **注文ランダム化**: ORDER 開始時に3レシピから注文を決定する。初回プレイはマルゲリータを
   優先し、Phase 1 からの体験の連続性を保つ。再プレイ時は直前の注文と異なるレシピを
   優先的に抽選し、「毎回違う注文が来る」楽しさを作る。
3. **トッピング配置改善**: 同一点付近への連続配置を防ぐため、既存トッピングとの最小距離を
   設け、近すぎる位置は少しずらして配置するか、それでも空きがなければ配置を拒否し
   視覚的フィードバック（✕マーク）を返す。スマホの tap 操作性を悪化させない範囲の
   閾値にとどめ、完全な物理シミュレーションは行わない。
4. **焼成の First Fun 強化**: 生焼け／いい焼き加減／焦げ の3状態をピザの見た目・焼成中の
   ゲージ演出・ブルーのリアクション・コメント・採点に一貫して連動させる。失敗しても
   ゲームオーバーにはせず、「次はうまく焼きたい」と思わせる失敗の見せ方にする。
5. **ミトのヒント強化**: 注文レシピごとに、不足している材料をキャラクターとして自然な
   短い会話で案内する（「○○が足りません」という無機質な表現にしない）。
6. **図鑑拡張**: 3レシピに対応し、未発見は「？？？」、発見済みは名前・使用材料・短い説明を
   表示する。新規発見時は軽い「NEW」演出を加える。

Phase 2A で明示的に対象外とするもの: 経営要素、お金、在庫、ログイン、サーバー、ランキング、
SNS、大量レシピ、ドラッグ&ドロップの全面刷新、音声、Phase 3 機能の先回り実装。

## 4. 非対象範囲（Out of Scope）

今回のフェーズでは実装しない。将来検討する場合も、必ず本ドキュメントの改訂を経てから着手する。

- ログイン・ユーザーアカウント
- 課金・アプリ内購入
- オンラインランキング・SNS共有
- 複雑な店舗経営（在庫管理、価格設定、従業員雇用など）
- 大量のレシピ・食材バリエーション（Phase 1 はマルゲリータ1種で十分）
- バックエンドサーバー・API通信・永続化DB（ローカル状態のみで完結）
- 過剰な自動テスト（E2E を大量に書かない。手動確認＋最小限の動作確認で足りる）
- MVP の完成条件に含まれない機能の先回り実装

## 5. ゲームループ

```
ORDER      ミトが注文を伝える（例: マルゲリータ）
  ↓
PREPARE    プレイヤーが生地にソースを塗り、チーズ・トッピングを配置する
  ↓
BAKE       「焼く！」を押す → 焼成演出 → 任意のタイミングで焼き上がりを確定する
  ↓
RESULT     ブルーが試食し、注文一致度・材料の正しさ・焼き加減を採点する
  ↓
DISCOVERED 完成したレシピが図鑑に登録される（初回のみ新規登録演出）
  ↓
（プレイヤー操作）もう一度作る → ORDER に戻る
```

この 5 状態（ORDER / PREPARE / BAKE / RESULT / DISCOVERED）が本プロジェクトのゲーム状態機械の正典である。
実装のステートマシンはこの名称・順序をそのまま用いる。

## 6. キャラクターの役割

| キャラクター | 役割 | 性格・立ち位置 | ゲーム上の機能 |
|---|---|---|---|
| テト（黒ポメラニアン） | 主人公・ピザ職人 | プレイヤーの分身。真面目で前向き | プレイヤー操作の代弁者。掛け声・進行セリフ |
| ミト（白ポメラニアン） | 注文・案内・ヒント | 元気で人懐っこい | ORDER で注文を伝える。PREPARE 中に迷ったときのヒントを出す |
| ブルー（ハスキー） | 試食・評価 | どっしり構えた食いしん坊 | RESULT で試食コメントと採点結果を伝える |

- キャラクター画像はユーザー提供の3枚（テト・ミト・ブルー）を正式なビジュアル参照とする。
- AIによる再生成でキャラクターデザインを変更しない。実装では提供画像をそのまま使用する。
- 将来キャラクターを追加する場合も、既存3キャラクターの見た目・性格設定は変更しない。

## 8. レシピ判定方式

- 各レシピは「必須食材の集合（カテゴリ別: ソース1種・チーズ0種以上・トッピング0種以上）」として定義する。
  - Phase 1 では「チーズ1種以上」を前提としていたが、Phase 2A でチーズを使わない
    マリナーラを追加したため、チーズは必須カテゴリではなく「レシピごとに定義された
    必須食材リストを満たすか」という汎用ルールに一般化する。
- 判定は **配置した食材の種類の集合** と **レシピが要求する食材の種類の集合** の一致度で行う。
  - 配置した「位置」や「個数」は自由（自分で作った感の演出のため）。
  - ただし「最低配置量」（例: チーズは画面上に一定量以上塗られている）を満たすかは PREPARE 内リアルタイムでガイドする。
- 一致度は以下の3要素に分解する:
  1. **必須食材の充足**（レシピが要求する食材をすべて使ったか）
  2. **余分な食材の有無**（レシピにない食材を使っていないか）
  3. **焼き加減**（BAKE で確定したタイミングが目標レンジ内か）
- Phase 1 ではマルゲリータ1種類のみのため、判定は「トマトソース・モッツァレラ・バジルの3種を使ったか」に単純化されていた。
  Phase 2A ではレシピごとに異なる必須食材リストと焼成目標レンジ（`bakeTarget`）を持たせ、
  同一のスコアリングロジック（`src/logic/scoring.ts`）だけでレシピが増えても判定できることを確認済み。
- 焼成タイミングは `bakeTarget` の範囲を基準に「生焼け（レンジ未満）／いい焼き加減（レンジ内）／
  焦げ（レンジ超過）」の3状態に分類し（`src/logic/bake.ts`）、ピザの見た目・ゲージ演出・
  ブルーの反応・採点で一貫して使用する。

## 9. 採点方式

RESULT 画面でブルーが 3 観点から採点し、総合評価を星（★1〜3）で表示する。

| 観点 | 内容 | 満点条件 |
|---|---|---|
| 注文一致度 | 注文されたレシピと完成ピザが一致しているか | 必須食材をすべて含み、レシピ名として認識される |
| 材料の正しさ | 使用した食材が過不足ないか | 必須食材を過不足なく使用（余分な食材がない） |
| 焼き加減 | BAKEフェーズで狙った焼成タイミングだったか | 目標レンジ（perfectゾーン）内で焼き上げ確定 |

- 各観点は 0〜100 のスコアを持ち、総合スコア = 3観点の平均。
- 総合スコアに応じて ★1（及第点）〜★3（パーフェクト）を表示。
- 採点はすべてローカルのデータ・ロジックで完結し、サーバー通信を必要としない。

## 12. 完成条件（Phase 2A の Definition of Done）

以下をすべて満たすことを Phase 2A の完成条件とする。

1. マルゲリータ・マリナーラ・クアトロ フォルマッジの3レシピが実装され、それぞれ
   ORDER → PREPARE → BAKE → RESULT → DISCOVERED まで一通りプレイできる
2. ORDER 開始時に3レシピからランダムに注文が決まり、初回プレイはマルゲリータが
   優先されること、再プレイでは直前と異なる注文が来ることを確認できる
3. トッピングを同一点付近に連続配置しようとすると、位置がずれる、または
   配置が拒否され視覚的フィードバックが出ることを確認できる
4. BAKE で「生焼け」「いい焼き加減」「焦げ」のいずれで取り出しても、ピザの見た目・
   ブルーのコメント・採点が状態に応じて変化し、ゲームオーバーにはならないこと
5. PREPARE 中、不足している材料についてミトが注文レシピに応じた自然な短いセリフで
   ヒントを出すこと
6. レシピ図鑑が3レシピに対応し、未発見「？？？」／発見済み（名前・材料・説明）を
   表示し、新規発見時に軽い演出があること
7. 基準画面幅 390×844 で ORDER/PREPARE/BAKE/RESULT/DISCOVERED の主要操作が
   1画面内に収まり、ピザが画面最大の視覚要素であること
8. `npm ci` / `npm run lint` / `npm run build` が成功し、既存 CI を壊さないこと
