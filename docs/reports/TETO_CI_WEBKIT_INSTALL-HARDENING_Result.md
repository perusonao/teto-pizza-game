# CI 基盤復旧 — WebKit インストールの失敗と 20 分制限（PR #622／#615 の WebKit 失敗の原因と修正）

- 種別: **CI 基盤のみ**（`.github/workflows/e2e-webkit.yml`、`scripts/ci/install-with-retry.sh`、`scripts/ci/test-webkit-ci.sh`）。テスト内容・シャード数（3）・テスト対象・Playwright の再試行（0）・`src`・`e2e`・本番設定は変更していません。skip・削除もありません。
- 調査日: 2026-10-22。対象: PR #622（`d0efd02`、WebKit run 39745814119）、PR #615（`aa8f507`、WebKit run 39737556165 の attempt 3）、main の post-merge run 39731795493（`d70bd20`）・39718286132（`83f4b55`）。
- 触っていないもの: #615（push なし）、#622、共有 Preview、本番 FINISH。いずれの PR も merge していません。

## 1. 結論

1. **PR #622 の WebKit 失敗はテスト失敗ではなく、環境（apt ミラー）が起点のインストール失敗＋リトライが自分で作った dpkg ロック競合です。** 失敗した 3 シャード（390×844 shard 1/3、360×800 shard 1/3、360×800 shard 3/3）は `Install WebKit` で止まり、`Run WebKit e2e` は **skipped**（実行 0 件、`listed 0, executed 0`）。
2. 連鎖は次のとおりです（§2）。①ランナーの apt ミラーが遅い → ②attempt 1 が 360 秒の上限で打ち切られる → ③`timeout` は **root で動く `apt-get`** を kill できず、`apt-get` は孤児として動き続けて `/var/lib/dpkg/lock-frontend` を保持する → ④5 秒後の attempt 2 が `E: Could not get lock ... held by process 2580 (apt-get)` で即失敗 → ⑤ステップ失敗。**ランナー同士（別 VM）の競合ではなく、同一 VM 内の自己競合**です。
3. **PR #615 の 390×844 shard 1/3 のキャンセルは、インストール 4 分 48 秒＋テスト 14 分 30 秒以上（未完了）がジョブ上限 20 分を超えたため**です（§3）。テスト内容の問題ではありません。
4. 修正（§5）: ①リトライの前に孤児の apt/dpkg の終了を（上限付きで）待つ。kill はしない ②1 回あたりのインストール上限 360 → 600 秒 ③ステップ上限 13 → 27 分 ④**ジョブ上限 20 → 35 分**。値の根拠は §4。
5. 検証: シェルテスト 107 → 123 件（負の対照で #622 の失敗を再現）。実環境（GitHub 上）での挙動は **この PR の WebKit 実行 1 回で初めて確認**されます（§7）。

## 2. PR #622 の WebKit 失敗：証拠

run 39745814119（HEAD `d0efd02`、テスト 1 行のみの変更）。11 チェックのうち WebKit の 6 シャード：

| シャード | 結果 | ジョブ時間 | インストール | テスト |
|---|---|---|---|---|
| 390×844 1/3（job 119713967292） | **失敗** | 7m02s | **6m12s で失敗**（08:11:47→08:17:59） | skipped |
| 360×800 1/3（job 119713967381） | **失敗** | 7m03s | **6m13s で失敗**（08:11:47→08:18:00） | skipped |
| 360×800 3/3（job 119713967406） | **失敗** | 6m55s | **6m11s で失敗**（08:11:40→08:17:51） | skipped |

同じ秒に開始した 6 ジョブで、インストールは **33 秒から 6 分超**まで開いています（ランナーごとのミラー速度の差）。`classify`・`build`・`layout-chromium`・Layout Contract Gate は成功。WebKit Gate は失敗（`FAIL-INFRA`：シャード証跡に `listed 0, executed 0`）。

390×844 shard 1/3 のログ（job 119713967292）の要点：
```
08:11:53  Need to get 117 MB of archives. (181 newly installed)
08:12:39  Get:3 ...  (3.5 MB の font に 45 秒)  ... ミラーの遅延が続く
08:17:47  ##[warning]attempt 1/2 timeout (exit 124)         ← 開始から 360 秒
08:17:47  Get:139 ... libgupnp-1.6-0                         ← timeout の後も apt-get が動いている（孤児）
08:17:52  ##[group]install attempt 2/2 ...
08:17:54  E: Could not get lock /var/lib/dpkg/lock-frontend. It is held by process 2580 (apt-get)
```

360×800 shard 3/3（job 119713967406）は孤児が **dpkg の展開段階**（`Selecting previously unselected package libdv4t64`）にあり、ダウンロードは終わっていました。つまり attempt 1 は「ほぼ完了」していたのに、上限と孤児で失敗扱いになりました。

**なぜ孤児が残るか**: `playwright install --with-deps` は `sudo` で root の `apt-get` を起動します。`timeout`（runner ユーザー）は `npx` と同じプロセスグループにシグナルを送りますが、root のプロセスには送れません（権限）。ログでも timeout の 10 秒後に別プロセス 2580 の `Get:` が続いています。

**同じ連鎖は過去にも出ていました**: PR #615 の最初の run（39737556165）の 390×844 shard 1/3 も「attempt 1 タイムアウト、attempt 2 が dpkg ロック競合」で、調査コメントに記録されています（#615 コメント 6335007227）。2 つの run で計 4 ジョブです。

**「同時インストール」「ランナー側の競合」について**: 別の VM 同士は dpkg ロックを共有しないため、シャード間の競合はありません。ロックを持っていたのは **同じジョブの attempt 1 の孤児**（プロセス 2580）です。ジョブ開始時点で他の apt が動いていた形跡（最初の試行でのロックエラー）は、見た範囲のログにはありません。ただし念のため、最初の試行の前にも待つようにしました（apt が動いていなければ即時戻るので無害）。

## 4. タイムアウト値の根拠（過去の成功ジョブ）

成功した 20 ジョブ（main の post-merge 2 run×6、#615 の 5、#622 の 3、#615 attempt 3 の 390×844 shard 2/3 を含む）の実測：

| 指標 | 最小 | 中央値 | 最大 |
|---|---|---|---|
| ジョブ全体 | 9m39s | 約 14m30s | **16m33s**（`83f4b55` の 390×844 shard 1/3） |
| テスト工程 | 8m29s | 約 12m27s | **14m58s**（同上） |
| インストール工程（成功 21 件） | 24 s | 約 40 s | **4m48s**（#615）。2m29s（#622）、3m23s（#615） |

インストール工程 24 件（成功 21、失敗 3）では、18 件が 1 分未満、3 件が 2.5〜4.8 分、**3 件が 6 分を超えて失敗**。

| 設定 | 旧 | 新 | 根拠 |
|---|---|---|---|
| ジョブ `timeout-minutes` | 20 | **35** | 正常時の最大 16m33s の 2.1 倍。遅いインストールでも成功するケース（1 回目が上限の 600 s に達し、孤児の待機 120 s、2 回目は短時間、最長のテスト 15 分、その他 2 分）で約 31 分。**20 分では旧 #615 のキャンセルを防げない**。 |
| インストール 1 回の上限 `--timeout` | 360 s | **600 s** | ログの 390×844 shard 1/3 は 360 秒で 153/187 パッケージ（約 82%）。残りのダウンロードと展開を足して約 8〜9 分と推定（推定値）。600 s でこの遅さが 1 回目で完了する。停止（進行なし）の検出ではなく壁時計の上限のまま。 |
| `--attempts` | 2 | 2（不変） | |
| インストールステップ `timeout-minutes` | 13 | **27** | 最悪（待機＋600 s×2＋kill 猶予）が約 24.6 分。これを超える分は壊れたミラーとしてステップで打ち切り、ジョブ上限（35）より前に失敗させる。 |
| 孤児の待機 `INSTALL_WAIT_SECS` | なし | 120 s（試行前・リトライ前） | 孤児が展開段階なら通常 1〜2 分で終わる。無期限には待たない。 |

`scripts/ci/test-webkit-ci.sh` に、これらの値の整合を縛るテストを追加しました（最悪ケースがステップ上限に収まる／遅いインストールの成功ケースがジョブ上限に収まる／ステップ上限がジョブ上限より小さい／ジョブ上限が 45 分以下）。
