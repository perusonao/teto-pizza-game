6. **進捗の数字が手書き**（レシピ 104／177 などを Result Report ごとに数え直している）。
7. `src/` の非テストファイルを全走査する Gate が複数あり（`.emoji` を読めるファイル、ladder を import できる経路、Preview 分離）、

## 2. 開発フロー（改善前 → 改善後）

```
改善前:  決定表 → [実装: 12〜14 ファイルを手で追記 → バッチテスト・E2E・HV シードを複製して書き換え
                  → 全テスト → 落ちた既存テストを 1 件ずつ直す ×N 回] → PR → CI → HV → merge

改善後:  承認スペック → preflight（#816）→ Owner 一括回答
          → scaffold → 実装スペックの TODO を埋める（文言・色・絵文字・サイズ）
          → claims → apply（約 3 秒）→ sweep（約 5 分で追従リスト全件）→ 全テスト → 生成済み E2E → PR → CI → HV → merge
```

| 工程 | 改善前 | 改善後 |
|---|---|---|
| 仕様の置き場 | 決定表（Markdown）＋ 12 ファイルに分散 | 実装スペック JSON 1 枚（`src/trainKit/landed/<tag>.json` として残り、契約テストの入力になる） |
| 本番データ | 手書き | `apply` が生成（アンカーが見つからなければ書かずに止まる） |
| floor・Reference 配置 | 手計算・コピー | 実 ladder と実 `assignReferenceSlots` から導出 |
| 既知の Gate 衝突 | 実装後に発覚 | `apply` が書く前に拒否（`other`、チーズ無し NO_SAUCE、焼成後ソース、絵文字重複 ほか） |
| バッチテストのデータ節 | 約 280 行を手書き | `trainContract.test.ts`（共通 1 本）がスペックを読む |
| HV シード・E2E | 複製して書き換え | テンプレートから生成 |
| 既存テストの追従 | 全テストで 1 件ずつ発見 | `sweep` が 1 回で列挙（直すのは人／モデル。期待値の自動書き換えはしない） |
| claim 重複 | 目視 | `claims`（Owner Gate と同じ規則を token なしで適用） |
| 進捗台帳 | 手で数える | `progress` が実カタログから計算 |
