## Authority reused (no second DISCOVERABLE logic)

`src/dev/discoveryProgressionModel.ts` calls only production code:

- `DISCOVERY_LADDER` (steps / materials) and `resolveShopEntitlement` (owned materials per step)
- `recipeDiscoveryState` (the DISCOVERABLE predicate)
- `selectHintTarget` (OPEN_POOL / TARGET, including the sticky case)
- `countsTowardLadder` (ladderCredit), `participatesInLunchRush` (lunchRush)
- `buildRecipeChapters` (Dex No.), `registerScoreToDex` (simulated Dex), `RECIPES` / `INGREDIENTS`

No recipe id, name, step or count is hardcoded. Tests spy on the three core authorities (they must be called) and compare every step against the existing production fixture (`walkState` / `poolOf` / `selectHintTarget`).

**Method.** Walk the canonical ladder order (first the starter-only recipe, then each step's key recipe). At step *s* the Dex holds the first *s* recipes. **After** = production predicate with step *s*'s materials; **Before** = the *same Dex* with only steps < *s* materials. Newly Discoverable = DISCOVERABLE after, not before. This isolates the unlock's own effect.

**Classification** (from `selectHintTarget`, not "candidates ≥ 2"):

| Result | Meaning |
|---|---|
| `NORMAL` | pool = 1 → `selectHintTarget` picks it automatically |
| `OPEN_POOL` | pool ≥ 2 and every member is new at this step → no sticky/purchased target can exist → OPEN_POOL |
| `OPEN_POOL POSSIBLE` | pool ≥ 2, but some members were already DISCOVERABLE before: with no maintained (sticky / purchased) target it is OPEN_POOL, but a kept target would still be a `TARGET` (verified through `selectHintTarget(..., {stickyRecipeId})`) |
| `NO POOL` | nothing DISCOVERABLE |

## 🆕 visualization

Inspector only (production UI untouched). Unlocked materials carry 🆕 in the list and the detail; the detail's「🆕 材料 → Newly Discoverable」section lists, per 🆕 material, which recipes it newly enables and how many of the After pool's members use it (flagging "all members use it = no clue"). Pool members are tagged 🆕 (new at this step) vs ↩前から (carried over). Example: at step 12 the 🆕 たまねぎ appears in 2/2 pool recipes, so it does not discriminate between the two; at step 18 the 🆕 チェリートマト appears in 1/2 (genovese only), which does narrow the pool.

## Read-only guarantee

- The model is pure functions over production constants; the Dex it builds is a local simulation value.
- The Inspector replaces `<App />`, so no player save is loaded or saved; the component holds only filter / search / open-rows state.
- Tests: production `RECIPES` / `INGREDIENTS` / `DISCOVERY_LADDER` JSON unchanged after building; `Storage.prototype.getItem/setItem/removeItem/clear` never called while building or interacting; a source scan forbids `persistence` / `gameReducer` / `localStorage` / `sessionStorage` / `indexedDB` / `firebase` / `dispatch(` in `src/dev` non-test files.

## Unreachable from normal production

- `?inspector=discovery` is parsed only behind `import.meta.env.DEV || import.meta.env.VITE_PREVIEW_MODE`; Vite folds it to a constant in production and the dynamic chunk is dropped.
- `previewIsolation.gate.test.ts` (real `vite build`) now also asserts the production bundle contains no `discovery-progression-inspector-v1` and a Preview bundle does.
- `inspectorAccess.test.tsx`: `<App />` with `?inspector=discovery` renders no Inspector; no production source outside `src/dev` / `src/main.tsx` mentions it; `main.tsx` imports it only dynamically inside the guarded branch.
- Note: `main.tsx` still statically imports `App` in DEV/Preview inspector mode, but never renders it.
