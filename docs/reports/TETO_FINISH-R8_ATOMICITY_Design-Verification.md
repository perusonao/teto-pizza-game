## 1. 結論

1. **Fresh Audit の推奨案 D（保存側の遅延）は、方針に反する。** 中断すると在庫が戻る（返却）。実測で再現した（§2）。D は撤回する。
2. **「返却なし」と「在庫・Dex の同時確定」は、焼成時点で何も追加保存しない限り両立しない**（§3）。両立には、焼成と同じ保存で「このラウンドを後で必ず完了できる情報」を残す必要がある。
3. 推奨は **最小の pending round（journal）を 1 つ足す方式（J-B）**。焼成の保存と同時に、消費済み在庫と「未完了ラウンド」の記録を書き、登録時に消す。次回起動時に未完了ラウンドがあれば、既存の純関数（`finalizeRound` と `REGISTER_TO_DEX`）で自動的に完了させる。保存形式の変更は **任意キー 1 つの追加のみ**（`schemaVersion` は 2 のまま）。
4. **Lunch Rush だけは journal を使わず、別扱いを推奨**（§6）。ラン自体がメモリのみで、リロードでラン全体が消えるため。
5. 実装は PR-3 の後（§8）。

## 2. 追加調査 1 — D 案の返却問題の再現

プローブ: fugazza（CUT あり、onion 20 → 5 個消費）を `CONFIRM_BAKE` 70 で焼き、D の保存値（メモリ上の在庫＋消費差分）を書いてリロード。既存の特性化テストと同じ fixture を使い、`vitest` で実行した。

| 観測 | 結果 |
|---|---|
| `CONFIRM_BAKE` 直後 | phase `POST_BAKE` / step `CUT`、onion 20 → **15**、`bakeResult` 70、`bakeState` perfect、completion PASS |
| D の保存値でリロード | onion = **20**（全額返却）、Dex 空、ラウンドは ORDER に戻る |
| アプリ内で「ホームへ」（`PLAY_AGAIN`、確認ダイアログ後） | onion = **15**（消費は確定）、Dex 空 |

評価:
- D では **アプリ内の中断は消費、リロード／強制終了は返却**となり、不整合。リロードの方が常に得なので、実質「焼成結果を見てからの無料やり直し」になる（§7 のとおり、結果は見えている）。
- コストはリロードだけ。得られるのは購入系の有限在庫の返却のみ（Starter は無限）。損害は小さいが、Owner 方針の「原則認めない」に反する。
- 現行（バリアなし）は逆に、返却はないが登録が失われる。

## 3. 追加調査 2 — 両立の可否（形式的な整理）

焼成結果が見えた後に:
- (R) 返却なし ⇒ 消費は焼成時点で **永続**でなければならない
- (A) 同時確定 ⇒ 登録も焼成時点で永続でなければならない
- (F) 保存形式を変えない ⇒ 登録に必要な情報は、既存の保存から復元できなければならない

登録に必要な情報（確定スコア、完成判定、Free の識別結果、Pitz の算出入力）は **メモリ上のラウンド状態にしかなく**、既存の保存からは復元できない。したがって (R)(A)(F) は同時には成り立たない。成り立たせる道は 2 つ:

- **E. 焼成時点で登録まで済ませる**（追加保存なし）。実現できる範囲が狭い（§4 の E）。
- **J. 焼成時点で、ラウンドを完了させるための最小情報を保存する**（追加保存あり）。

### J-B の設計

保存（焼成確定 `CONFIRM_BAKE` の保存と **同一の setItem**）:

```
inventory: 消費後（現行どおり、メモリと同じ値）
pendingRound?: { v:1, roundId, kind: GUIDED|FREE_COOK, recipeId?(Guided), bakeValue, pizza: <sanitized PizzaState> }
```

- 在庫は **メモリ上と同じ値を常に保存**する。D0 のような保存側の遅延・足し戻しは不要になり、RESTOCK との合成問題も消える。
- 登録（`REGISTER_TO_DEX`）の保存では、Dex／Pitz／（FINISH の最終消費）と `pendingRound: null` を **同一 setItem** で書く。
- 次回起動時に `pendingRound` があれば、reducer の新アクション（例 `SETTLE_PENDING_ROUND`）が、保存済みのピザ構成で POST_BAKE を既定で完了（CUT 線なし、FINISH で何も置かない）させ、既存の `finalizeRound(FINAL)` → `REGISTER_TO_DEX` を **1 回だけ**実行。保存は 1 回の setItem（Dex／Pitz／`pendingRound` 削除）。
- 新しい採点・登録ルールは作らない。「中断＝最後の確定ボタンを何もせず押した結果」と定義するだけ。
- 効率ボーナス（所要時間）は付かない（`completedMs` がない）。
- 後乗せが必須のレシピ（本番にはまだない）は、FINISH で何も置かなければ完成判定が FAILED になり、登録されない。消費は確定したまま。これは「仕上げを放棄した」結果として同じ定義で説明できる。
- 無効・肥大した `pendingRound` は読み込み時に破棄する（フォールバック＝現行の「消費のみ」）。

アプリ内の中断との整合: 現在の「ホームへ」（POST_BAKE で `PLAY_AGAIN`）は消費のみで終わる。クラッシュ時だけ自動完了させるとここがずれるため、**アプリ内の中断も同じ自動完了に統一**するのが一貫する（Owner 判断 §9-3）。

### 保存形式への影響

- 追加は任意のトップレベルキー `pendingRound` のみ。`schemaVersion` は 2 のまま。既存セーブは無修正で読める（キーなし＝従来どおり）。
- 古いビルドが書き込むと、このキーは落ちる可能性が高い（`writeSave` は既知フィールドから組み立て、保持される extras は ID 系の台帳に限られる。`persistence.ts` L682–）。落ちた場合は「消費のみ」の現行挙動に退化し、それ以上の破損はない。
- 要確認: `saveRootClassification`・`saveQuarantine`・サニタイザ・将来の v3 移行が、このキーを既知として扱うこと。
- **サイズは未計測。** `sauceDeposits` は量の上限でしか制限されず、点数の上限がない（`sauceLedger.ts`）。実装時に実測し、上限を超えたら journal を書かず現行挙動に退化させる。

## 6. Lunch Rush の扱い

J-B は Lunch Rush に使えない。登録の可否が**提供期限の判定**（`handleMissionServeNext` が期限後の登録を拒否）で決まり、起動時に再現できない。ランの時計・メトリクスもメモリのみで、リロードでラン全体が消える。

提案（Owner 判断 §9-4）:
- **L-1（推奨）**: 次の注文へ進む（またはランを終える）まで、そのピザの消費も保存しない（D0 の挙動を Lunch Rush にだけ適用）。リロードするとランが丸ごと消え、時計・成績・未受領の報酬も失うため、1 枚ぶんの在庫返却による「無料やり直し」の得はコストに見合わない。「ランが保存上なかったことになる」と整合する。窓中の RESTOCK は §7 のとおり UI から到達不能なので、足し戻しのずれは起きない（念のため差分の足し戻し方式で合成可能）。
- L-2: 現状維持（消費は焼成時に確定、BEST のみ失う）。
- L-3: ラン全体の journal（過剰。不採用）。

## 8. 追加調査 7 — PR-3（ロード基準値ガード）との整合

- PR-3 のブランチは origin に未 push で、実コードは見られない。**#560 のクレームコメントの記述にのみ基づく**判断である。
- PR-3 の範囲: 起動時の読込結果（成功した生テキスト／失敗）をセッションに保持し、`writeSave` 直前に保存内容と照合。不一致（読込失敗後、別タブの更新）は書込拒否。R8 は範囲外と明記。
- 整合（J-B）:
  - 焼成時の journal 書込と登録時の書込は、どちらも通常の `writeSave` 経路。PR-3 が拒否すれば、その書込は「全部書かれない」ので不整合は生じない。
  - 起動時の自動完了は、読込結果を基準値にして書くため、PR-3 の照合を通る。
  - **二重完了の防止**: 同じ journal を 2 つのタブが見た場合、先に完了したタブが保存を書き換える。後のタブの登録書込は、保存内容が基準値と違うため PR-3 に拒否される。拒否されたタブは通知を出す。つまり exactly-once は PR-3 の基準値ガードに依存する。`roundId` を付け、完了を行うのは起動時にそれを読んだセッションだけにする。
- 衝突: J-B は `persistence.ts`（読み書き・サニタイズ）と `App.tsx`（起動時の完了、保存 effect）に触れ、どちらも PR-3 の HOT file。**PR-3 の merge 後に着手**し、新テストは別ファイルに置く（`persistence.*.test.ts` は PR-3 のクレーム glob 内）。
- D0／L-1 は `persistence.ts` を触らず、`App.tsx` の 1 式のみ。

## 9. 推奨方式と Owner 判断事項

### 推奨（まとめ）
1. Guided／Free／Research（CUT・FINISH 含む）: **J-B**（焼成と同時に消費と pending round を保存、登録で消す、起動時に既存関数で自動完了）。
2. Lunch Rush: **L-1**（ランが保存上なかったことにする。そのピザの消費も登録時まで保存しない）。
3. Dinner: 変更なし。
4. 保存形式: 任意キー `pendingRound` 1 つ。`schemaVersion` は 2 のまま。

### Owner 判断事項
1. **J-B（保存形式の追加を許容する）で進めるか。** 追加しない場合は「返却なし」と「同時確定」のどちらかを諦める必要がある（§3）。諦めるなら、現行（消費のみ・登録なし）か D0（返却あり）を選ぶ。
2. 自動完了の定義: 「中断＝何もせず確定した結果」でよいか。効率ボーナスは付かない。後乗せ必須レシピは FAILED（消費のみ）になる。
3. **アプリ内の中断（ホームへ）も同じ自動完了に統一するか。** 現在は破棄（消費のみ）。統一しないと、クラッシュとアプリ内中断で結果が変わる。
4. Lunch Rush: L-1（推奨）／L-2／L-3 のどれか。
5. journal 肥大時の退化（現行挙動）を許容するか。サイズ上限の値は実測後に確定。
6. 自動完了後に見せるもの（前回ピザの結果サマリーを起動時に出すか、無言で保存だけするか）。UI／HV の判断が必要。
7. PR-3 merge 後に着手でよいか。#560 から分割 Issue を立てるか。

## 10. テスト計画

1. **特性化→要件化**: `persistence.compat.progress.test.ts` の R8 `it.todo` を満たす行列。{Guided 非CUT, Guided+CUT, Guided+FINISH, Free+FINISH（opt-in）, Research} × {BAKE 直後, CUT／FINISH 中, 確定直前, 確定直後} で、保存→リロード→**「在庫が消費後で、Dex に登録済み」**、または**どちらも変化なし**（焼成前）。「消費のみ」と「返却」はどちらも失敗。
2. **返却不可**: 窓中のリロード後、在庫は消費後の値であること（今回のプローブを回帰テスト化）。
3. **自動完了**: 構成の復元結果が、手動で「何もせず確定」した場合と **バイト同一**（Dex／Pitz）。Pitz の二重付与なし（exactly-once）。
4. **journal の寿命**: 登録の保存で `pendingRound` が消える。失敗・FAILED 結果でも消える（消費は確定）。壊れた／肥大した journal は破棄され、現行挙動に退化する。
5. **失敗系**: 焼成の書込成功→登録の書込失敗、容量超過、PR-2 の書込拒否状態、`requireDinnerRecords` 拒否。
6. **二重完了**: 2 つのセッションが同じ journal を見ても、登録は 1 回（PR-3 の基準値ガード併用）。
7. **互換**: 既存の保存互換テスト・golden が無修正で通る。`pendingRound` なしの保存は従来とバイト同一。古いビルドの書込で journal が落ちても破損しない。往復テスト。
8. **Lunch Rush（L-1）**: 結果画面でリロード→在庫は焼成前。「次の注文へ」後は確定。窓中の RESTOCK を足し戻しで合成。ラン終了／ホーム復帰の経路で漏れなく確定。
9. **Dinner**: 消費・保存挙動が現行と同一（回帰）。
10. **E2E（390×844、Chromium＋WebKit）**: FINISH opt-in の Free で FINISH 中にリロード→前回ピザが登録され、在庫が戻らないこと。CUT レシピでも同様。
11. **HV**: 起動時の自動完了の見え方は UI 変更に当たるため、方針（`TETO_HUMAN-VERIFICATION-POLICY.md`）に従う。
