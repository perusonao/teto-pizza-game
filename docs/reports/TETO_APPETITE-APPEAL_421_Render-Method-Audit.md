1. **凸性**: 写真の溜まりは凹凸のある形（0.76〜0.84）。ゲームの試作は全て 0.95〜1.0（ほぼ完全な凸）。**形の再現ができていないことを直接示す指標**。

3. **縁**: 写真は中心の明るさが縁のすぐ内側まで続き、縁の外は数 px で急に落ちる（比較的くっきり）。Proto4/4b の羽化した縁は写真より柔らかい（0.38〜0.56 対 0.08〜0.27）。Owner の写真所見の「縁が薄く半透明」は**一部の縁だけ**で、全周ではない。

## 3. 現行 CSS 方式で楕円形から脱却できない原因（項目 1）
1. **形の部品が凸だけ**: 要素は `border-radius` の角丸矩形で、背景のグラデーション・影・ローブはいずれも「凸な楕円の和」。凸な図形の和は、重ねても**くびれ・切れ込み（凹）を作れない**（凹を作るには引き算＝`mask`・`clip-path`・SVG フィルタが必要）。→ 凸性が 0.95〜1.0 から動かない（§2-1）。
2. **引き算の手段が封じられている**: #467（古い WebView の疑い）対策で、`clip-path`・疑似要素・追加 DOM・`mix-blend-mode`・SVG フィルタを使わない制約を置いている。Proto 全般がこの内側で試作された。
3. **広がりを transform で表現**: `scale` / `skew` は縦横比を変えるだけで形の複雑さは増えない。実際、縦横比が写真の 1.1〜1.4 から 1.5〜2.4 へ離れた（§2-2）。
4. **縁をぼかしで表現**: グラデーションのフェザーは縁を柔らかくする方向にしか働かず、写真の「くっきりした縁＋一部だけ薄い」と逆（§2-3）。
5. **層数と描画の兄弟**: 形を出そうとするほど背景層・影層が増え、描画コストが上がる（Proto4 は M1 比 +17〜28%。4b で層を減らして +7%）。
6. **質感の指標が合っていない**: 中心が明るすぎ・白飛びが多い（§2-4）。これは方式ではなく色設計の問題で、方式を変える際に同時に直す。

## 4. SVG パス方式（項目 2）
- **実現性: 高い（形の面では）。** 1 個ごとに閉じたパス（放射状にずらした 8〜12 点を滑らかな曲線で結ぶ。決定的ハッシュ）を描けば、凹凸のある輪郭・くっきりした縁・個体差を直接作れる。塗りは `linearGradient` / `radialGradient`、焼き色は小さな楕円の `radialGradient`。**フィルタ・`clip-path`・`mask` は不要**。
- **足りない部分**:
  - 厚みの陰影（縁の暖かい帯、薄い所の透け）は、フィルタ無しだと**段階的に縮めたパスの重ね**か、**線幅を変えた縁取りの重ね**で近似するしかなく、表現が階段状になる。
  - 隣り合う溜まりの**融合**は、パスの合成（ブーリアン演算）ができず、半透明の重なりで二重に濃く見える。
  - 凹凸のある外形に対する中心→縁の勾配は、`radialGradient` では表せない（凹の所で破綻）。
- **性能・影響の懸念**:
  - 焼成中は毎フレーム `d` 属性を組み直す。要素数は 1 個あたり約 6〜8、CUT では**ピースごとに複製**（6 ピース × 溜まり数）され、DOM が数百ノード増える可能性。
  - **既存の SVG フィルタ（`PieceReliefFilter`、#418 のカット断面の照明）が `.pizza-pieces` 全体に掛かっている**。チーズのパスもその高さマップに入り、縁に断面の陰影が付く（意図しない見た目）。外す・除外するには既存の見た目の検証が要る。
  - #467（LINE 内ブラウザなど。保留中）の疑いは SVG フィルタが対象とみられ、フィルタ無しの素の SVG は低リスクと推測するが、**実機未確認**。
  - 性能は未計測（Chromium では軽いと見込むが、毎フレームの属性更新とノード数の影響は測っていない）。

## 5. Canvas 方式（項目 3）
- **実現性: 高い。既存に先例があります。** `SauceHeatmapCanvas`（64×64 の密度場を作り、アルファ曲線で画素化して 200px のキャンバスへ。共有の作業面、決定的、単体テスト・Chromium/WebKit の画素 e2e つき）と `OverflowMarkerCanvas`。CUT でも全ピースに同じ画素のキャンバスを複製する仕組みが既にある。
- **写真の特徴との相性**: 「厚みの場（高さマップ）」を 1 つ計算し、そこから**形（しきい値）・縁の鋭さ（しきい値付近の勾配）・透け（薄い所のアルファ）・陰影（高さの勾配から計算する艶消しの照明）・焼き色（薄い所に出る滑らかなノイズのしきい値）**を全て作れる。境界関数を放射状の角度ごとの半径（低次の調和＋舌状の盛り上がり＋切れ込み）にすれば、**凹凸のある形（星形）**を決定的に生成できる。複数ピースを 1 つの場に入れれば融合も自然に出る。
- **性能（概算、Node でのマイクロベンチ。試作ではなく見積り用）**: 画素ごとに `atan2`・`cos` を毎回計算する素朴な実装は、96×96・3 個で 5.3ms/回、128×128・8 個で 23.6ms/回と重い。**角度ビン・半径・ノイズを 1 回だけ前計算し、フレームごとには「溶けに依存する縮尺・厚み・照明」だけを評価**すると、**96×96 × 3 個で 0.6ms、8 個で 1.6ms、128×128 × 3 個で 1.1ms**（Node の JIT 暖機後。モバイルは 3〜6 倍遅いと見て 2〜4ms 程度）。再描画は溶けを約 24 段階に量子化すれば約 28 回/秒で足りる。→ **JS の計算は M1 の描画（ラスタ）と同じ桁で、ぼかし層を増やす CSS より軽い見込み**。実測は未実施。
- **既存ゲームへの影響**:
  - 採点は配置座標を使い、チーズの見た目は読まない（影響なし）。
  - PREPARE・トレー・Reference・サムネイルは生の見た目のまま（CSS のまま）。**焼成〜RESULT の溶けたモッツァレラだけ**をキャンバスに置き換える（`MELT_SHAPE_CHEESE_IDS` の opt-in を流用）。
  - ピースの DOM（配置・回転のラッパ）は残し、中の描画だけを `<canvas>` にする。CUT のピース複製は、描いたビットマップを共有して複製する。
  - `getContext` が使えない環境（jsdom、古い WebView）は現行 CSS（M1）へ**フォールバック**。
  - 影響を受けるテスト: `mozzarella-melt-421.spec.ts`、`finished-pizza-visual-2.0.spec.ts`、`PizzaStage.bakeVisual.test.tsx`（`.pizza-cheese--mozzarella` の計算済みスタイルを見ている部分は、キャンバス画素の判定に置き換え）。`PieceReliefFilter` の高さマップにはチーズのキャンバスも入る（縁の陰影が付くか要確認）。
- **懸念**: 小さなキャンバスの拡大でエッジが甘くなる（出力は CSS サイズの 2 倍以上で描き、アルファの勾配を急にして対応）／iOS のキャンバスメモリ／`ctx.filter`（Safari の対応が不確か）は使わない設計にする／アクセシビリティ上は装飾なので `aria-hidden`。

## 7. 1 個の焼き上がりチーズを作る最小実装案（項目 5）
**純関数 `renderCheesePool(seed, melt, toast, char)` → `ImageData`（ピースごとの小さな局所キャンバス、約 96×96）** を作り、`<canvas>` に描く。DOM・採点・保存には触れない。
1. **境界**: 角度ごとの半径 R(θ) = R₀ × (1 + 低次調和 k=2〜5 の和) に、1〜2 個の舌状の盛り上がり（角度のガウス）と 0〜1 個の切れ込みを加える。パラメータはピースの鍵（`ingredientId:x:y`）のハッシュから決定的に決め、`Math.random` は使わない。
2. **厚み場**: ρ = 距離 / R(θ)。高原 = 1 − ρ⁴ を基本に、低周波ノイズで 0.8〜1.0 に変調。縁は急に落ちる（縁の幅 ≈ 等価直径の 4〜5%）。舌状の部分は高原を低く（薄く）する。
3. **色**: 基本色 (238,234,218) を、厚みに応じて縁側で (226,216,192) へ。アルファは厚み×係数（薄い所は透けて赤みが出る）。
4. **陰影**: 厚みの勾配から左上光源のランバート（±6%、艶消し）＋縁の左上に細い照り。
5. **焼き色**: 滑らかなノイズのしきい値 × 薄さ。`toast` で琥珀、`char` で茶。数 % の面積。
6. **動き**: 溶けの 24 段階に量子化した結果をメモ化。Proto3 の振付（締まる→広がる→落ち着く）は残すが、**広がりは縦横比の引き伸ばしではなく面積の拡大（等方）**。`prefers-reduced-motion` は最終形のみ。
7. **性能の約束**: 角度ビン・半径・ノイズをピースごとに 1 回だけ前計算。フレームごとは 縮尺×厚み×照明だけ。
8. **配線（別スライス）**: `PizzaStage` の BAKE/CUT/RESULT で、モッツァレラのピースだけ `<canvas>` を描く。生の見た目・トレー・Reference は不変。`getContext` 失敗時は現行 CSS。

## 8. 方式の比較と推奨（項目 6）
| 観点 | 現行 CSS（Proto4b まで） | SVG パス | Canvas（場の計算） |
|---|---|---|---|
| 凹凸のある外形（凸性） | ✕（0.95〜1.0 のまま） | ◎（パスで直接） | ◎（境界関数＋しきい値） |
| くっきりした縁＋局所的な薄さ | △（ぼかしが前提） | ○（縁はくっきり。薄さは近似） | ◎（高さ場から） |
| 厚みの陰影・艶消しの質感 | △（層が増える） | ✕〜△（フィルタ無しでは階段状） | ◎（勾配から照明） |
| 焼き色の局所性 | △（斑点のグラデーション） | ○ | ◎ |
| ピースの融合 | ✕ | ✕（二重の濃さ） | ◎（場の合成。任意） |
| 描画・計算コスト | M1 比 +7%（Proto4b、層 7） | 未計測（毎フレームの属性更新＋ノード数。CUT で複製） | 見積り 0.6〜1.6ms/回（前計算あり）。実測は未実施 |
| 既存コードへの影響 | 小 | 中（`PieceReliefFilter`・DOM 増・複製） | 中（置換は焼成〜RESULT のみ。テスト更新あり。先例あり） |
| #467・WebKit のリスク | 低 | 中（SVG。フィルタ無しなら低とみるが未確認） | 低〜中（`getContext` のフォールバック。ctx.filter は使わない） |
| 実装規模 | — | 小〜中 | 中 |

**推奨: Canvas 方式（ピースごとの小さな局所キャンバス＋場の計算、S1→S2 の順）。** 理由: (1) CSS では構造上、凸性を動かせない（§3）。(2) SVG は形は作れるが、厚み・艶消しの質感と融合が弱く、`PieceReliefFilter` や DOM の複製に絡むため、写真の「厚みのある溜まり」への到達が不確か。(3) Canvas は、形・縁・厚み・焼き色を 1 つの場から作れ、既存のソース表示で先例（決定的・テスト・WebKit の画素 e2e・CUT での複製）がある。**次点は SVG パス（形だけ先に出す案）**。CSS 方式の追加調整は推奨しません。

## 9. リスクと未確認
- 写真は 1 枚のみで、溶ける過程（時間変化）は静止画から分からない。動きは Proto3 の振付を参考にした仮説。
- 写真の測定は傾向の比較用（JPEG・バジル欠け・ピザ直径の推定の不確かさ）。ゲームの描画は Chromium の画像。実機（Safari）は未確認。
- Canvas の性能はマイクロベンチによる見積りで、実機・実トレースは未実施（S2 の合格基準で測る）。
- `PieceReliefFilter` とチーズのキャンバスの相互作用（縁に出る陰影）は S2 で要確認。
- 古い WebView（#467）での Canvas は未検証。

## 10. Owner への確認事項
1. 推奨（Canvas、S1→S2）で進めてよいか。次点（SVG の形だけ先行）を先に試すか。
2. 写真のコピーをリポジトリで共有できるか（ライセンス確認済みのもの）。共有できない場合は、数値目標（§6）を正として進める。
3. 広がりを「引き伸ばし」から「面積の拡大（等方）」に変えることの承認（Proto3 の方向修正）。
4. ピース同士の融合（S3）を最初から入れるか、後回しか。
5. `prefers-reduced-motion` は「最終形のみ」でよいか。
